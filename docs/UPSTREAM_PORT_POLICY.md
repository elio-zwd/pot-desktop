# Pot 社区维护版上游 PR 移植政策

## 1. 目的

本政策用于将上游 `pot-app/pot-desktop` 的有价值修复安全地引入 `elio-zwd/pot-desktop`，同时避免整批接管上游遗留 PR、混入无关修改或丢失原作者署名。

## 2. 分支命名

每个移植候选使用独立分支：

`port/upstream-pr-<number>-<topic>`

示例：

`port/upstream-pr-1285-aliyun-https`

分支必须从当时最新的 `custom/main` 精确 SHA 创建，不得从上游 PR 分支或旧功能分支继续开发。

## 3. 审计输入

开始移植前必须读取：

- 上游 PR 的完整 diff；
- PR 讨论、review、关联 Issue 与关闭原因；
- 原始提交 SHA、作者和提交历史；
- 上游 CI 结果及失败日志；
- 新增或变更依赖；
- 受影响模块的当前维护版实现；
- 与当前 Schema V2、Windows x64 和安全边界的重叠情况。

只看 PR 标题、单个提交或关闭状态不足以作出结论。

## 4. 评估维度

### 安全性

- 是否修复明文传输、凭据泄露、任意代码执行或用户数据破坏；
- 是否引入新的网络端点、权限、脚本执行或不受控渲染；
- 是否需要真实密钥、证书或用户数据才能验证。

### 稳定性

- 是否影响启动、快捷键、剪贴板、插件安装、插件执行或更新器；
- 是否有竞态、平台差异、错误恢复和回滚路径；
- 是否会破坏旧版插件或已稳定的 Schema V2。

### 相关性

- 是否直接服务 Windows x64、插件平台、安全或主要接口；
- 是否只影响未正式支持平台或低使用率服务；
- 是否已有维护版替代实现。

### 规模与维护成本

- 是否包含多个互不相关模块；
- 是否要求整体升级依赖或迁移 Tauri 2；
- 是否能拆成可独立验证的小 PR；
- 后续维护者是否能解释和验证关键代码。

## 5. 移植方式

优先顺序：

1. 原提交可直接重放且历史清晰时，优先保留原作者 commit；
2. 需要适配当前主线时，保留原作者 Authorship，并在提交说明中记录上游 SHA；
3. 必须重写时，在提交或 PR 中使用标准 `Co-Authored-By`，并说明与原实现的差异；
4. 不得复制代码后删除来源信息或把原作者工作表述为维护版原创。

提交信息继续使用 `英文 Tag: 中文描述`。

## 6. 拆分要求

- 一个分支只处理一个可独立说明和验证的问题；
- 跨安全、UI、依赖、发布和运行时多个模块的大 PR 不得整体移植；
- 与当前任务无关的格式化、依赖升级和重构必须删除或另开分支；
- 与 Result Schema V2 或设置 Schema V2 重叠的改动必须先比较语义，禁止覆盖现有兼容实现。

## 7. 验证要求

移植后必须在最新 `custom/main` 上执行：

- 与修改直接相关的测试；
- 两组 Schema 测试，若变更可能触及插件设置或结果链；
- `pnpm build`；
- 目标平台的必要人工验证；
- `git diff --check` 和工作区干净检查；
- 对安全或网络改动执行端点、凭据和明文传输审计。

上游 CI 通过不能替代维护版验证。

## 8. 四种结论

每个候选必须在 `UPSTREAM_PORTS.md` 记录以下结论之一：

- **接受**：范围明确、风险可控，进入独立移植分支；
- **拒绝**：与维护范围无关、风险过高或维护成本不可接受；
- **等待**：缺少复现、验证资源、上游信息或依赖前置条件；
- **替代实现**：问题有效，但原 PR 不适合直接移植，改用更小或更安全的实现。

## 9. Draft PR 要求

移植 PR 必须保持 Draft，正文至少说明：

- 上游 PR、原始提交和作者；
- 审计结论与拆分理由；
- 实际移植文件；
- 与上游实现的差异；
- 测试结果和未覆盖风险；
- `UPSTREAM_PORTS.md` 对应记录。

未经仓库所有者明确授权不得转 Ready 或合并。
